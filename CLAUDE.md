# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A 2U fork of Instructure's Canvas iOS apps (Student, Teacher, Parent). The Student app is the actively shipped target here (bundle prefix `com.instructure.icanvas.2u`); 2U additions include offline downloads (`mobile-offline-downloader-ios`, `Core/Core/DownloaderClient`, `Core/Core/UIDownloads`), DataDog logging/RUM, and Firebase Remote Config. The code is licensed under AGPLv3, and every source file carries the license header (`yarn update-headers` adds missing ones).

## Restricted Commands

Do NOT run any git commands (e.g. `git status`, `git pull`, `git push`, `git log`, `git fetch`, `git commit`). Leave all git operations to the user.

Do NOT build the project or run tests (e.g. `xcodebuild`, `xcodebuild test`, `yarn test`, `yarn coverage`). The commands below are documented for reference only.

## Setup & Commands

Always open `Canvas.xcworkspace`. Xcode projects for **Core** and **Student** are generated by XcodeGen from `project.yml`, so edit the YAML, not the `.xcodeproj`. Teacher and Parent `.xcodeproj` files are checked in directly.

```sh
make provision      # brew bundle (xcodegen, swiftlint, node, yarn, cocoapods) + sets git commit template
make sync           # regenerate Core and Student xcodeproj via xcodegen (run after adding/removing files)
make sync-ci        # CI variant: Student uses project-ci.yml (no code-sign team settings)
```

- Dependencies are Swift Package Manager packages declared in `Core/project.yml` and `Student/project.yml` (with Student target configs split into `Student/*/*.yml` includes).
- Lint: `swiftlint` from the repo root (config `.swiftlint.yml`; it also runs as a pre-build phase via `scripts/xcode-build-phases/swiftLint.sh`). Line length warns at 200; function bodies are capped at 100 lines.
- Tests: `yarn test --scheme Core` (or `--scheme Student`, optionally `--os <version>`), and `yarn coverage --scheme <SCHEME>` for coverage. A single test runs with `xcodebuild test -workspace Canvas.xcworkspace -scheme Core -only-testing:CoreTests/<TestClass>/<testMethod>`. Test plans live in `TestPlans/`.
- Secrets (e.g. PSPDFKit licenses) are cases in `Secret.swift` and generated as data assets with `yarn build-secrets "key=value" ...`. See `documentation/secrets.md`; never write real secret values into files.
- Icons: `yarn build-icons` converts instructure-icons SVGs to PDF assets.

## Architecture

A detailed write-up is in `documentation/architecture.md`.

### Targets
- **Core** (`Core/Core`) is a shared framework holding nearly all features, models, networking, persistence, and UI. App targets are thin shells.
- **Student / Teacher / Parent** each contain an AppDelegate, a `Routes.swift` route table, and only app-specific screens.
- **Student** also contains the `SubmitAssignment` share extension and `Widgets`. Core is built with `APPLICATION_EXTENSION_API_ONLY`, so Core code must be safe to use from an app extension.
- **TestsFoundation** (`Core/TestsFoundation`) holds shared test helpers, mocks, fixtures, and E2E/UI test infrastructure. **CoreTester** is the host app for `CoreTests`.

### Core layout
- `Core/Core/Common/CommonModels/` holds the infrastructure: `API`, `Store`, `Router`, `AppEnvironment`, `Analytics`, `DataDog`, `Logger`.
- `Core/Core/Common/CommonUI/` holds shared UI, including `InstUI` (the design-system components and `InstUI.ScreenState`), `CoreWebView`, and view modifiers.
- `Core/Core/Features/<Feature>/` is organized by feature (Assignments, Courses, Modules, Pages, Inbox, Planner, …).

### AppEnvironment
`AppEnvironment.shared` is the service locator that holds `api`, `database` (a CoreData `NSPersistentContainer`), `router`, `currentSession`, `logger`, `userDefaults`, and the current `app` (`.student`/`.teacher`/`.parent`). Many components take an `env: AppEnvironment` parameter so tests can inject a test environment.

### Data layer (two coexisting patterns)
1. **The UseCase + Store pattern (older and pervasive):** a feature defines
   - `APIX` Codable response models,
   - a `GetXRequest: APIRequestable`,
   - a CoreData `NSManagedObject` model, and
   - a `GetX: UseCase`/`CollectionUseCase` struct.

   The struct supplies `cacheKey`, `request`, `scope` (the predicate and sort used to read from CoreData), and an optional `write`. `Store`/`ReactiveStore` runs the use case: it fetches from the API, writes the result to CoreData, and publishes the cached objects (with a TTL that defaults to 2 hours). The data model is `Core/Core/Resources/Database.xcdatamodeld`. See `Features/Pages/GetPages.swift` for a minimal example.
2. **MVVM + Interactor (newer, SwiftUI):** generated from `.github/templates/Canvas/MVVM Module.xctemplate`. Each module has:
   - a `XInteractor` protocol, with an `XInteractorLive` implementation and an `XInteractorPreview` for previews,
   - an `XViewModel: ObservableObject` exposing `state: InstUI.ScreenState`, and
   - an `XScreen` SwiftUI view.

   An `XAssembly` enum with static `make…` factory functions wires these together and is what routes call (e.g. `PlannerAssembly.makeEventDetailsViewController`). Prefer this pattern for new screens.

Older screens are UIKit view controllers with storyboards and a static `create(...)` factory.

### Navigation
Navigation is URL-based. Each app builds a `Router(routes: [RouteHandler("/courses/:courseID/...") { url, params, userInfo in ... }])` in its `Routes.swift` and installs it on `AppEnvironment`. Screens navigate with `env.router.route(to: "/path", from: viewController, options: ...)`. A new screen needs a `RouteHandler` in each app that uses it. Student routes are covered by `Student/StudentUnitTests/RoutesTests.swift`.

### Strings
Strings are localized with String Catalogs (`Localizable.xcstrings`). Core code uses `String(localized: "...", bundle: .core)`.

## Testing
- Unit tests subclass `CoreTestCase` (`Core/CoreTests/TestHelpers/CoreTestCase.swift`). It sets up an in-memory database and test environment, and provides `api.mock(...)` overloads that stub responses per `APIRequestable` or `UseCase`.
- E2E tests (`*E2ETests`) use the UI test helpers in `TestsFoundation`.

## Conventions (`.github/guidelines/`)
- Follow `.github/guidelines/swift-style-guide.md`. The README asks for "fat model, thin controller": put logic in models, interactors, and view models so it can be unit tested.
- **Commit message format, enforced by Danger (`dangerfile.js`).** The first commit of a PR must include:
  ```
  <title>

  refs: MBL-XXXX        (or none)
  affects: Student, Teacher
  release note: ...     (or none)
  test plan:
  - ...
  ```
  The template is in `.gitcommit`. Recent commits on this fork use free-form `fix:`-style titles with PR numbers instead.
- PR checklist: test on phone and tablet, in light and dark mode, and check accessibility.
